# Thin delivery coordination

SPARK guides methodology; pi-subagents owns execution. Delivery binds the approved plan and exact configured models, supplies context/results, and displays progress. Do not build a second execution loop.

1. Read repository instructions and relevant project memory. Use SPARK brainstorming/planning, debugging, TDD and verification as appropriate. Resolve genuine requirements questions in conversation; never ask again about approved decisions.
2. Enable `/delivery on` only when requested. If routes are missing, inspect `delivery_configure` and ask the user to select exact provider/model IDs via `/delivery setup`. Never infer capability or price from a model name. Existing routes need no repeated setup. Combined review uses `quality`; retained `spec` configuration is unused.
3. Call `delivery_plan` with mode, title, tasks (instructions, literal relative files/directories, acceptance, task-specific executable checks, optional sensitive flag), final checks, and security flag. No Markdown file is required. For an existing plan, read it and preserve its scope in this proposal. Task files are starting points/context, not a permission list: directly necessary repository files/tests may be changed without per-file approval. Dirty work is allowed; preserve unrelated preexisting edits even within touched files. Implementation plans bind the configured security route before approval for sensitive paths discovered later; never silently select or reconfigure a model.
4. Wait for explicit conversational approval of the displayed unchanged plan. `Approved`, `Implement the displayed plan`, or `/delivery approve` approves it. Questions, planning-only requests, model attestations and earlier approvals never launch. `delivery_execute` starts only after the real approval turn; changed plans/routes/workspace require a new proposal.
5. The flow is implement → task checks → fresh combined specification/quality review → security review when sensitive. Failed task checks or concrete review findings can trigger at most two correction rounds with unchanged approval. Coder diagnoses and fixes task-related failures within the approved product task, reporting choices rather than asking path permission. Every correction reruns checks and independent reviews. Review all actual changed paths accumulated across corrections, not only original hints; independent reviewers reject unrelated changes. Final checks run only after all tasks pass their reviews. Final-check failures remain blockers because the coordinator cannot reliably attribute plan-wide failures to tasks; do not invent automatic recovery or replay completed tasks.
6. `delivery_status` returns actual check receipts, reports and known native identity. Do not call subagent tools directly, execute shell commands or edit while coordinating. Never manufacture checks, approvals or successful worker closure. Read-only review mode permits no host commands or fixes; set every checks array to []. Supply existing evidence in task instructions instead.
7. For a completed review with no retained worker, do not call `delivery_resume` or poll status. If the user says continue and the intended implementation is clear, prepare the implementation proposal directly with `delivery_plan`; do not ask whether they want a plan. Resolve only material unanswered requirements. Implementation still requires approval of the displayed implementation plan; completed review approval never authorizes writes. A completed implementation has nothing to resume; do not invent additional work. For continue on a retained v2 worker, call `delivery_resume` without new approval; it shares `/delivery resume` handling. Do not ask the user to type commands the model can call. `delivery_stop` shares `/delivery stop` handling and requests cancellation only, not closure. Same-process reload can monitor the same live worker. After full restart, reclaim requires the current journal fence and exact canonical repository/session UUID/delivery run, conclusively dead previous Pi owner and exact native worker ID/directory/owner with validated observed `process-terminal.json` proof. Native proof includes runner close and any subprocess writer-tree closure; status labels, candidate records and PID death alone are not proof. A stale-fence diagnostic requires inspection of the latest retained state, not retrying an earlier worker's proof. Never revive or replace a retained worker, replay accepted coding/checks, kill PIDs, delete locks or alter journals. A successful retained reviewer can finish; failed workers remain explicit failures; native stopped workers or a prior stop request settle as stopped, even if a successful report arrived.
8. Infrastructure failures stop with actionable diagnostics, never automatic retries or alternative models. Report the actual missing evidence and next action from the tool result. Living/unknown owners or workers, foreign identities, missing/pending/malformed proof and pending host checks remain blocked. The spawning parent's native runner-close observer publishes terminal proof; restarting before observation can leave it unavailable. Preserve artifacts and seek native tooling support if the indicated evidence cannot be established. Do not repeat approval/status/stop or prescribe another restart as recovery. Approval while blocked is not authority to execute another plan. Unsupported old journals are preserved and cannot resume or migrate. Old running sessions are not hot-migrated and the old per-file approval modal is not generated here: settle/inspect workers and preserve partial work before using a fresh session.

Autonomy stays within the approved product task: new requirements, genuinely ambiguous outcomes, destructive actions, new dependencies/provider changes and unrelated work remain unauthorized. Escalate those decisions, not directly necessary file paths or task-related check failures. Never traverse symlinks or write outside the repository.

No optimizer, execution profiles, alternate review policies, automatic Git writes, cleanup, candidate adoption, recovery budgets or publication. Report terminal findings; do not generate replacement plans for blocked or exhausted runs. A user-requested next step after a completed review may prepare a proposal without a separate permission-to-plan question. No OS sandbox is claimed; approved commands run with the user's permissions. Reviewers have strict native read/grep/find/ls tools, not shell/browser/write access.
